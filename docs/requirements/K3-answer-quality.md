# 需求卡片：K3-答案质量（Prompt 重构 + 上下文元信息 + 引用校验）

> **本积木解决的核心痛点**：用户反馈"弹出来的内容不太符合实际用户的要求"。
> **先分清两件事**：
> ① 若 `.env` 里 `RAG_PROVIDER=mock` → **内容差是必然的**，`MockLLM`（`app/providers/mock.py:49-55`）
>    的设计就是"不做总结、只把含数字/标准代号的原文句子摊开"，它自己都标注了"未经大模型总结"。
>    这是**没配 Key**，不是功能缺失。
> ② 配了真 Key 之后内容仍可能不达预期 → 那是**本积木要修**的：prompt 太简陋、
>    上下文缺元信息、无引用校验。

## 一句话

重写 `Generator` 的 prompt（system/user 分离 + 上下文带来源元信息 + 分点结构 + 拒答分级），
把文件名提前到生成之前，生成后校验引用编号有效性。让模型能说出"根据《供应商管理制度》
第 4.2 条…"而不是笼统的"资料显示"。

## 背景与动机

`app/rag/generator.py:11-23` 的现状：单个 user message、3 条要求、上下文只有 `[i] 正文`：

```
你是企业内部知识库问答助手。请仅依据下面提供的资料回答用户的问题。
{history}【资料】
{context}
【用户问题】
{query}
要求：
1. 用简体中文回答，简明准确；
2. 回答中引用某条资料时，在对应句子末尾标注来源编号，如 [1]、[2]；
3. 若资料中没有相关信息，请明确说明「资料库中未找到相关信息」，不要编造。
```

四个具体缺陷：

1. **无 system 角色**。真模型（qwen-plus / GLM）对 `system` 的指令遵循度显著高于
   混在 user 里的指令；现在全部塞进一个 user message，指令权重被正文稀释。
2. **上下文没有元信息**。模型只看到 `[1] 正文…`，**不知道这段来自哪份文档、第几块**，
   所以它永远说不出带出处的回答。而 `pipeline.py:105-113` 的 `_attach_filenames`
   是**生成之后**才执行的——信息在生成时根本不存在。
3. **没有结构要求**。没说"先给结论再分点"，真模型默认写一大段散文；用户看到的
   就是"一大坨"。同一份资料，结构化输出比散文的可读性差距极大。
4. **拒答只有一刀切**。"资料库里没有"这个单一分支无法处理最常见的中间态：
   资料只覆盖了问题的一部分、或两份资料互相冲突。模型此时倾向于自己脑补。

### 附带发现（可立即验证，零代码）

`app/config.py:53` 默认 `chunk_strategy = "fixed"`，而定长递归切块**不含章节标题**。
`split_structure` 会把标题段落在该块开头（`chunker.py:196-210`：标题作为 `buf` 起点）。
所以**把 `CHUNK_STRATEGY` 改成 `structure`，块内自带「4.2 五金件标准」这类标题行，
模型引用条款号的能力会立刻上一个台阶**——这是本积木里性价比最高的一步，
不需要写代码，改配置 + 重新摄取即可验证。

## 方案

### 1. Provider 层支持 system（`app/providers/`）

- `base.py`：`LLMProvider.complete(prompt, *, system=None, max_tokens=1024)`；
  `stream()` 同签名。
- `openai_compat.py`：`system` 非空时拼成 `[{"role":"system",...},{"role":"user",...}]`。
- `mock.py`：忽略 `system`（其 `_parse_prompt` 只认 `【用户问题】`/`【资料】` 标记，
  模板标记保留即可零改动）。

### 2. 上下文元信息（`app/rag/pipeline.py` + `generator.py`）

- **把 `_attach_filenames` 提前到生成之前**（`ask()` 与 K1 的 `ask_stream()` 都要改），
  使 `SourceRef.filename` / `ScoredChunk` 在拼 prompt 时就可读。
- `Generator.build_prompt()` 为每块渲染一行来源头：
  ```
  [1]（来源：供应商管理制度.pdf · 第 3 块）
  4.2 五金件标准
  …正文
  ```
- **可选增强（纯正则、不动表结构）**：从块首抽取 `^\d+(?:\.\d+)*\s+\S+` 形态的标题行
  作为 `section` 提示。**不新增数据库列**——SQLite 分支没有迁移路径
  （`create_all()` 不给已存在的表加列，项目已踩过一次），这一约束必须守住。

### 3. Prompt 重构（`generator.py`）

**system**（角色与规则，一段）：

```
你是企业内部知识库问答助手。只依据【资料】回答，资料没写的一律不推测。
输出要求：
- 先一句话直接回答，再分点展开；要点不超过 5 条
- 每个要点末尾标注来源编号，如 [1][3]；同一要点可引多条
- 引用编号必须来自【资料】中真实存在的编号，不得杜撰
- 资料只能部分回答时，先答能答的，再明确说明哪部分资料未覆盖
- 多份资料冲突时，并列说明分歧并指出各自来源，不要自行裁决
- 资料完全无关时，只回「资料库中未找到相关信息」
用简体中文。
```

**user**（资料 + 问题 + 历史）：

```
{history}【资料】
{context}
【用户问题】
{query}
```

### 4. 引用校验（生成后处理，`generator.py`）

- 正则抓 `\[(\d+)\]`，与 `chunks` 数量比对：
  - 超界（如只有 5 块却出现 `[7]`）→ 记录告警日志 + 计入返回的 `citation_issues`
  - 一个引用都没有 → 记录（说明模型没遵守格式）
- **不自动删改正文**（会破坏可读性、也可能误伤）；只做**可观测**，供质检台与
  问答日志统计"引用有效率"，这也是一个可讲的技术点。

### 5. 可配置项（`app/config.py`）

- `llm_temperature: float = 0.2`（现在硬编码在 `openai_compat.py:25`）
- `llm_max_tokens: int = 1024`（现在硬编码默认值）
- `answer_style: str = "structured"`（`concise` | `structured` | `detailed`）
- `citation_check: bool = True`

## 子块

| 子块 | 功能 | 说明 |
|------|------|------|
| K3-0 | `CHUNK_STRATEGY=structure` + 重新摄取验证 | **零代码**，先做，立竿见影 |
| K3-1 | `LLMProvider.complete/stream` 支持 `system` | Mock 忽略即可 |
| K3-2 | `_attach_filenames` 提前 + 上下文带文档名/块号/章节 | 两处调用点（ask / ask_stream） |
| K3-3 | system/user 分离的 prompt 重构 + 拒答分级 | 核心 |

| K3-5 | temperature / max_tokens / answer_style 配置化 | — |

## 输入 / 输出

- `AskResponse` 新增可选字段：`citation_issues: list[int] = []`（超界的引用编号）
- 对外请求结构不变

## 验收标准（可测试）

- [ ] `Generator.build_prompt()` 输出的 context 每块含文档名与块号（字符串断言）
- [ ] 无历史时 prompt 不含【对话历史】块（J1 回归不变）
- [ ] `MockLLM` 在新模板下仍能正确解析出 query 与各块（`_parse_prompt` 回归）
- [ ] 引用校验：构造含 `[9]` 而只有 5 块 → `citation_issues == [9]`；无引用 → 记录为空列表且不报错
- [ ] `system` 参数：`OpenAICompatLLM` 用 stub 断言 messages[0].role == "system"；
      传 None 时退化为单条 user（向后兼容）
- [ ] **人工评测**（真 Key）：准备 6 个问题（含 2 个答案不在库内的、1 个需跨两份文档的），
      改前/改后各跑一遍，按 4 维打分：答到点 / 无幻觉 / 引用有效 / 结构可读。
      目标：6 问中 ≥5 问"答到点"，幻觉 0 例，引用有效率 ≥90%
- [ ] 现有 187 测试全绿

## 依赖

- 前置：**必须先能连真 Key 实测**，否则无法判断 prompt 改动是否有效
- 与 K1 关系：K1 做完后再做本积木，迭代评测时不用盲等
- 与 K3-0 关系：`chunk_strategy=structure` 需**重新摄取已有文档**才生效，
  验证时注意旧库里的块仍是 fixed 切的

## 不做什么（边界，防止范围蔓延）

- **不新增数据库列**（heading/section 字段）→ 保住 SQLite 无迁移的现状
- 不做答案的自动引用重排/重编号
- 不做"答案自评/自动打分"（属于更大的评测体系，单独排）
- 不做 few-shot 示例（先把基础 prompt 效果测出来，有效果不够再加）
- 不改检索引擎的召回逻辑（prompt 只影响"用给定资料怎么答"，别甩锅到检索）
- 不做多模型对比评测框架（K7 的模型切换做完再说）

## 失败点 / 风险

- **无法归因**：prompt 改了好几处，效果变好/变差不知道是哪一处。→ 严格按子块顺序做，
  每个子块单独跑一次那 6 个问题并记录。
- **上下文变长导致成本与延迟上升**：加元信息会增 token。→ 元信息行控制在一行、
  非正文；评测时同时记录首字节延迟与总耗时。
- **引用校验误伤**：模型可能输出 `[1-3]`、`[1,2]` 等变体导致正则漏抓。
  → 正则需覆盖 `\[\d+(?:\s*[-,，]\s*\d+)*\]`，并对未匹配形态只记 debug 日志。
- **`_attach_filenames` 提前引入额外查询**：每个请求多一次 `Document` 查询。
  → 只查命中的 ≤top_k 个 document_id，可接受；若与 K6 缓存叠加需注意失效。
- **`structure` 切块让部分文档块数变化** → 质检台/文档健康的历史数据与新数据不可比，
  需在 progress-log 记录切换点。
- **MockLLM 模板解析被打乱**：改模板时务必保留 `【资料】` 与 `【用户问题】` 两个字面标记，
  否则离线全量测试会集体失败。
