# 需求卡片：G6-数据看板

> 每张卡片 = 一个功能积木。实现前先填好，做完后在 `progress-log.md` 更新状态。
> 2026-10-06 从「后续候选」拆卡（grill-me 定案：范围四块、入口进下拉）。

## 一句话
把 G4 问答日志、K5 反馈、K6 缓存命中三份已落库的数据变成一页可决策的界面——
常问什么、缓存省了多少、用户满不满意、哪些文档是死的，打开看板就知道。

## 输入 / 输出
- 输入：`GET /api/kbs/{kb_id}/dashboard`（一次聚合返回全部块，viewer+ 可读）
- 输出：KB 级看板页 `/kbs/:kbId/dashboard`——概览统计卡（复用 StatCard）+
  常问问题 TOP 10 + 「没用」原因分布 + 死文档清单；入口在 KbsList「更多 ⌄」下拉

## 验收标准（可测试，逐条打勾）
- [x] 聚合正确：同一问题问 4 次 → 累计问答 4、缓存命中 3、TOP1 count=4
- [x] 反馈聚合：有用 1 + 没用 1（带原因）→ 反馈数 2、有用率 50%、原因分布正确
- [x] 死文档复用 G5 命中统计（`compute_hit_stats` 抽成共享函数，两页一个真相源）
- [x] 空知识库全零不报错；非成员 403
- [x] 前端不引图表库：榜单用 el-table（DocHealth 先例），统计卡复用 StatCard
- [x] 双端测试全绿；`vue-tsc` / `vite build` 通过；真数据验收（dev 库 qa_logs 有真实积累）

## 依赖
- 前置积木：`G4-问答日志`、`K5-反馈`、`K6-缓存`（三张表即数据源）、`K7-StatCard`（组件复用）

## 不做什么（边界，防止范围蔓延）
- 不做时间趋势图（会诱惑引图表库；等真实需要再拆）
- 不做导出 / 跨库汇总 / 自动刷新；死文档明细不重复做（链接到「索引体检」）
- 不建新表、不引新依赖

## 失败点 / 风险
- 聚合查询多表 join（feedback 无 kb_id，需 message→conversation 两跳）——与
  `list_feedback` 同款 join，模式有先例
- TOP 问题的缓存命中映射：`query_cache.query_norm` 与 `qa_logs.query` 规范化后对齐
  （复用 `normalize_query`，同一 norm 多参数行时求和）
